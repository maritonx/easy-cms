# ADR-0065: Easy CMS เป็น application engine แบบ code-first

- **สถานะ:** Accepted
- **วันที่:** 2026-11-08
- **คำโปรย:** แทนโดย [ADR-0069](0069-typescript-backend-six-levels.md) (TypeScript backend ครบในตัว, roadmap หกระดับ) การตัดสินใจอื่นยังใช้
- **เกี่ยวข้อง:** [ADR-0004](0004-code-first-content-model.md) (ยืนยัน), [ADR-0018](0018-plugin-endpoints-admin-components.md), [ADR-0030](0030-plugin-pages-and-dashboard.md), [ADR-0064](0064-calendar-view.md)

## บริบท

- เป้าหมายของเจ้าของโปรเจกต์: Easy CMS ไม่ได้เป็นแค่ที่จัดการบทความ นักพัฒนาต้องใช้สร้างระบบให้ลูกค้าได้หลายแบบ
  เช่น CRM, ระบบจอง และร้านค้า (grilling 2026-11-08)
- ข้อเสนอจากภายนอกที่นำมาคุยมีสองทางที่ขัดกัน: ให้ผู้ใช้สร้างทุกระบบเองในหน้า admin แบบ no-code
  หรือเพิ่มความสามารถให้นักพัฒนาแบบ code-first
- สิ่งที่มีอยู่แล้ว (origin/main, 1.39.1):
  - component ของ field (`admin.component`, `admin.after`, `admin.cell`), field `ui`, `admin.sidebar`
  - หน้าและแผง dashboard ของตัวเอง (`admin.pages`, `admin.dashboard`)
  - รายการแบบตาราง (saved views), ต้นไม้ และปฏิทิน (`admin.calendar`)
  - `endpoints` ใน config และ plugin
  - `admin.brand` ตั้งชื่อ โลโก้ และสีหลัก
- สิ่งที่ยังขาด:
  - ปุ่มที่รันโค้ดฝั่ง server (⌘K มีแค่ลิงก์, bulk action มีเฉพาะที่ระบบกำหนด)
  - Kanban
  - หน้ารายการแบบของตัวเอง และพื้นที่ฟอร์มแบบของตัวเอง
  - ฟอนต์, favicon และ CSS ของตัวเอง

## การตัดสินใจ

- **code-first ต่อไป:** นักพัฒนาประกาศโครงสร้างใน `easy-cms.config.ts` ซึ่งอยู่ใน Git, มี type และ review ได้
  ส่วนลูกค้าของนักพัฒนาใช้หน้า admin
  - **ยืนยัน ADR-0004:** ไม่ทำ UI builder สำหรับ collection และ field
  - ให้ admin เพิ่มบางอย่างเองแบบจำกัด (hybrid) ค่อยพิจารณาเมื่อมีกรณีใช้จริง
- **สองชั้น:**
  - ความสามารถพื้นฐานที่ทำให้ระบบหลายแบบสร้างได้
  - template ของ `create-easy-cms` ที่พิสูจน์ว่าพอจริง (CRM, ระบบจอง)
  - ไม่ทำ plugin ระบบธุรกิจขนาดใหญ่ เช่น CRM เพราะดูแลยาวและเฉพาะทางเกินไป
- **ชื่อและคำโปรย:**
  - คงชื่อ Easy CMS
  - คำโปรยใช้แต่สิ่งที่พิสูจน์ได้ด้วยตัวอย่างจริง ไม่ใช้ "ทุกระบบ" หรือ "ปรับแต่งได้ 100%"
  - ปรับเว็บหลัง actions, Kanban และ CRM template ออก
- **Custom actions:**
  - ประกาศใน config ได้ทั้งปุ่มบนเอกสาร, row action และ bulk action ที่รันโค้ดฝั่ง server
  - มีสิทธิ์, การยืนยันก่อนกด และผลลัพธ์ที่แสดงให้เห็น
  - รายละเอียด grill ใน issue ของตัวเอง
- **หน้ารายการแบบของตัวเองเป็น view:**
  - component ได้รับทั้งข้อมูลที่ระบบเตรียมให้ (ผลลัพธ์ตามคำค้นและตัวกรอง, จำนวน, query, รายการที่เลือก)
    และ `api` สำหรับดึงข้อมูลเอง
  - เปลี่ยน query และเลือกเอกสารผ่าน event ระบบจะโหลดใหม่ อัปเดต URL และใช้ bulk action ของระบบได้
  - เป็น view ที่สลับกับตารางได้ หรือแทนตารางทั้งหมดด้วย `default: true`
  - นักพัฒนาที่ต้องการแค่หน้าตาใช้ข้อมูลที่ระบบให้ ส่วนที่ต้องการคุมทั้งหมดดึงเองผ่าน `api`
    ผู้ใช้ปลายทางไม่เสียคำค้น ตัวกรอง saved views และ bulk action
- **Kanban เป็นของในตัว:**
  - สร้างบนกลไก view เดียวกัน เพื่อพิสูจน์ว่าสัญญาพอ
  - ไม่ให้แต่ละคนเขียนเอง เพราะต้องทำงานกับคีย์บอร์ด สิทธิ์ และการบันทึกให้ถูกต้อง
- **พื้นที่ฟอร์มแบบของตัวเอง (`admin.edit.component`):**
  - แทนเฉพาะพื้นที่ฟอร์ม ส่วนหัว, บันทึก, ฉบับร่าง, ประวัติ, ล็อก, autosave, live preview และแถบข้างยังเป็นของระบบ
  - ใช้สัญญาเดียวกับ component ของ field: ได้ค่าของเอกสาร และส่ง `set-field` / `change`
  - ระบบบันทึกและตรวจความถูกต้องให้
  - ไม่เปิดให้แทนหน้าแก้ไขทั้งหน้า เพราะจะทำให้ข้อมูลเสียหรือหลุดระบบความปลอดภัยได้ง่าย
    ถ้าต้องการคุมทั้งหน้าจริง ๆ ใช้ `admin.pages`
- **ธีม:**
  - ฟอนต์: เปิด CSP เฉพาะโดเมนฟอนต์ที่ประกาศ
  - favicon
  - `admin.css`: path ของไฟล์ที่ระบบส่งให้แบบเดียวกับ `admin.modules` ไม่ต้องแตะ CSP
- **สัญญาของ CSS:**
  - รับประกันเฉพาะตัวแปร CSS (`--brand`, `--surface`, `--radius`, ฟอนต์ ฯลฯ) และจุดเกาะ `data-ecms="..."`
    ที่จะไม่เปลี่ยนโดยไม่แจ้งใน changelog
  - selector อื่นใช้ได้แต่ไม่รับประกัน และเอกสารต้องเขียนข้อนี้ให้เห็นชัด
- **ลำดับ:** actions → Omise ([#86](https://github.com/maritonx/easy-cms/issues/86)) → custom list views →
  Kanban → ธีม → พื้นที่ฟอร์ม → CRM template → Booking template → ปรับคำโปรยบนเว็บ
  - actions มาก่อน เพราะเปลี่ยนที่เก็บข้อมูลให้เป็นระบบงานมากที่สุด และ Omise ได้ใช้ทันที (คืนเงิน, ตรวจสถานะการจ่าย)

## ผลที่ตามมา

- ✅ จุดแข็งเดิมยังอยู่: type ครบ อยู่ใน Git review ได้ และความเข้ากันได้ที่สัญญาไว้ใน 1.0 ไม่ต้องรื้อ
- ✅ ช่องว่างจริงเล็ก: มีเพิ่ม 6 อย่าง ทั้งหมดเป็น option ใหม่ ไม่ breaking
- ✅ template เป็นทั้งตัวพิสูจน์และตัวอย่างสำหรับคำโปรย
- ⚠️ ไม่แข่งกับ Directus หรือ Airtable ในกลุ่มคนไม่เขียนโค้ด และลูกค้าของนักพัฒนายังสร้าง collection เองไม่ได้
- ⚠️ view, พื้นที่ฟอร์ม, ตัวแปร CSS และจุดเกาะ `data-ecms` กลายเป็นสัญญาที่ต้องรักษาตามนโยบายเวอร์ชัน
- ⚠️ CSS ที่เกาะ selector อื่นอาจพังเมื่ออัปเดต admin ซึ่งเป็นความเสี่ยงของผู้ใช้ตามที่เอกสารบอกไว้
