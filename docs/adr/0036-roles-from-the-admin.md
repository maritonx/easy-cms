# ADR-0036: บทบาทและสิทธิ์จากหน้า admin (RBAC)

- **สถานะ:** Accepted
- **วันที่:** 2026-10-05

## บริบท

- บทบาทเป็นรายการตายตัวใน config (`auth.roles`) และสิทธิ์เป็นฟังก์ชัน `access` ในโค้ด การเพิ่มกลุ่มผู้ใช้หรือปรับสิทธิ์จึงต้องให้นักพัฒนาแก้โค้ดและ deploy ใหม่ทุกครั้ง
- มีตารางติ๊กสิทธิ์อยู่แล้วสำหรับ API key (`ApiKeyPermissions`) ซึ่งตรวจซ้อนบน `access` และ `/admin/schema` ส่งสิทธิ์ของผู้ใช้ให้หน้า admin อยู่แล้ว

## การตัดสินใจ

- **เปิดเองใน config:** `auth: { rbac: true }` โปรเจกต์ที่ไม่เปิดทำงานเหมือนเดิมและไม่มีตารางเพิ่ม
- **collection ภายใน `user-roles`** (slug จองไว้ ไม่ใช้ `roles` เพราะโปรเจกต์อาจมี collection ชื่อนี้อยู่แล้ว): `key` (unique เปลี่ยนไม่ได้), `name`, `permissions` (`{ collections, globals, admin }`) จัดการผ่าน `/admin/roles` เท่านั้น ไม่เปิดผ่าน REST ทั่วไป
- **`users.role` ยังเก็บ key เป็นข้อความ** และผู้ใช้หนึ่งคนมีบทบาทเดียว โค้ดเดิมอย่าง `user.role === 'admin'` จึงใช้ได้ต่อ เมื่อเปิด `rbac` field นี้เปลี่ยนจาก select เป็น text (คอลัมน์เดิม ไม่ต้อง migrate ตาราง users) ตรวจตอนบันทึกว่าเป็นบทบาทที่มีอยู่ และ `/admin/schema` แปลงกลับเป็น select ที่มีตัวเลือกจากตาราง
- **สิทธิ์ = `access` ในโค้ด AND บทบาท:** ตรวจที่ `checkGrant` ใน Local API จุดเดียว (แทน `checkKey` เดิม ซึ่งตรวจ API key ด้วย) ทุกช่องทางที่ใช้ `overrideAccess: false` จึงได้ผลเหมือนกัน (REST, MCP, endpoint ของ plugin)
  - `admin` ทำได้ทุกอย่างเสมอ แก้สิทธิ์และลบไม่ได้
  - request ที่ไม่ได้ login ใช้ `access` อย่างเดียว เนื้อหาสาธารณะจึงยังสาธารณะ
  - collection ภายในและ `api-keys` ไม่อยู่ในตาราง (มีกฎของตัวเอง)
  - `users`: ถ้าบทบาทไม่มีสิทธิ์อ่านหรือแก้ไข ยังได้บัญชีของตัวเองเสมอ (คืน where `{ id: user.id }`) ส่วน `role` และ `active` ยังแก้ได้เฉพาะ admin ด้วย field access เดิม
  - API key ทำงานในนามเจ้าของ จึงได้ไม่เกินบทบาทของเจ้าของไปเองโดยไม่ต้องเก็บอะไรเพิ่ม หน้า admin ให้ติ๊กเฉพาะสิ่งที่เจ้าของทำได้
- **หน้าใน admin ที่ให้สิทธิ์ได้:** `status`, `deliveries`, `page:<path>` และ `widget:<tag>` (กล่องบนแดชบอร์ดระบุด้วย tag จึงต้องไม่ซ้ำเมื่อเปิด `rbac` และเพิ่ม `label` ที่ไม่บังคับ) ส่วน Backups, Email และ Roles เป็นของ admin เท่านั้น เพราะไฟล์ backup มีทั้งฐานข้อมูล และหน้า Email ส่งอีเมลออกไปนอกระบบ หน้าของ plugin ต้องผ่านทั้ง `access` ของหน้าและบทบาท
- **ค่าเริ่มต้นแบบไม่อนุญาต:** collection, global และหน้าที่เพิ่มทีหลังไม่มีบทบาทไหนได้สิทธิ์ แถวที่ยังไม่มีบทบาทใดเคยถูกบันทึกไว้เลย (ไม่มี key ใน `permissions`) แสดงป้าย "ใหม่" การบันทึกบทบาทจึงเก็บทุกแถว รวมแถวที่ไม่ได้ติ๊ก (`[]`)
- **สร้างข้อมูลตั้งต้นเมื่อใช้ครั้งแรก ไม่ใช่ตอนเปิดระบบ** (เพราะ `easy-cms migrate` เปิด CMS ก่อนที่ตารางจะมี): เพิ่มบทบาทใน `auth.roles` ที่ยังไม่มี และถ้าตารางว่าง บทบาทที่ไม่ใช่ admin ได้ทุกสิทธิ์ของ collection, global และหน้าของ plugin ที่มีตอนนั้น (เท่ากับที่ทำได้ก่อนเปิด `rbac`) ส่วน status และ deliveries ยังเป็นของ admin เหมือนเดิม
- **บทบาทใน `auth.roles` ลบไม่ได้** (โค้ดอาจตรวจอยู่) แต่เปลี่ยนชื่อและสิทธิ์ได้ บทบาทที่สร้างใน UI ลบได้เมื่อไม่มีผู้ใช้ (409 ถ้ายังมี)
- **cache สิทธิ์ในหน่วยความจำ** ล้างเมื่อบทบาทถูกแก้ และอ่านใหม่อย่างน้อยทุก 30 วินาทีสำหรับหลาย instance
- **ประวัติ:** ทุกการสร้างและแก้เก็บเป็น version (parent `user-roles`) พร้อมผู้แก้ เปิด `rbac` จึงเพิ่มตาราง versions ด้วยถ้ายังไม่มี
- **หน้า admin:** สิทธิ์ `publish` เพิ่มใน `/admin/schema` (ปุ่มหลักเป็น "บันทึกฉบับร่าง" เมื่อไม่มีสิทธิ์เผยแพร่) และ `views` บอกหน้าที่ผู้ใช้เปิดได้ ช่อง relationship และ upload ที่ชี้ไป collection ที่อ่านไม่ได้แสดงค่าเดิมพร้อมข้อความ "ไม่มีสิทธิ์เข้าถึง" และค่าไม่หายเมื่อบันทึก หน้า Roles เตือนกรณีนี้ตอนแก้บทบาท

## ผลที่ตามมา

- ✅ admin เพิ่มกลุ่มผู้ใช้และปรับสิทธิ์ได้เองโดยไม่ต้องแก้โค้ดหรือ deploy
- ✅ กฎในโค้ดยังเป็นเพดาน การเปิดใช้ไม่เปลี่ยนพฤติกรรมเดิมจนกว่าจะเอาติ๊กออก
- ⚠️ ต้อง migrate ตาราง `user-roles` ครั้งเดียวเมื่อเปิดใช้
- ❌ ยังไม่มีสิทธิ์ระดับ field และ "เฉพาะเอกสารที่ตัวเองสร้าง" (ต้องเพิ่ม `createdBy`) ใช้ `access` ในโค้ดไปก่อน
- ❌ ผู้ใช้หนึ่งคนมีได้บทบาทเดียว
