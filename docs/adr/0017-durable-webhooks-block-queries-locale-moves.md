# ADR-0017: Webhook ที่ไม่หาย, ค้นหาข้างในบล็อก และย้ายข้อมูลเมื่อเปลี่ยนภาษาเริ่มต้น

- **สถานะ:** Accepted
- **วันที่:** 2026-09-27

## บริบท

ADR 0014–0016 ทิ้งข้อจำกัดไว้สามข้อ: webhook ที่รอส่งซ้ำอยู่ในหน่วยความจำ (process ดับแล้วหาย),
ใช้ where กับข้อมูลในบล็อกไม่ได้ และเปลี่ยน `defaultLocale` แล้วคอลัมน์ชื่อเดิมกลายเป็นของอีกภาษา

## การตัดสินใจ

**Webhook ที่ไม่หาย**
- เพิ่ม internal collection `webhook-deliveries` เฉพาะเมื่อมี `webhooks` (แบบเดียวกับ versions/scheduled-jobs)
- บันทึกลงคิวก่อนส่งครั้งแรก และลบเมื่อสำเร็จ (0.8: เดิมบันทึกเมื่อครั้งแรกล้ม ซึ่งยังหายได้ถ้า process ดับระหว่างส่ง)
  แลกกับการเขียนฐานข้อมูลเพิ่ม 2 ครั้งต่อ event ต่อ webhook ส่วน transaction เดียวกับการบันทึกเอกสาร (outbox เต็มรูปแบบ)
  ไม่ได้เลือก เพราะ hook ของผู้ใช้เรียก cms ซ้อนได้ ถ้าครอบไว้ใน transaction เดียว SQLite จะ deadlock
- รายการถูกบันทึกทีละรายการตามลำดับ event การส่งครั้งแรกจึงเริ่มตามลำดับ event เหมือนเดิม
- ลองใหม่เร็วๆ 2 ครั้ง (1 วิ, 5 วิ) ในหน่วยความจำ แล้วต่อด้วยคิวในฐานข้อมูล: 1 นาที, 5 นาที, 30 นาที, 2, 6, 12 ชั่วโมง แล้วเป็น `failed`
- เก็บ body เป็นข้อความตามที่ส่งครั้งแรก (ไม่ใช่ JSON) เพราะ jsonb ของ Postgres เรียงคีย์ใหม่ ทำให้ลายเซ็นเปลี่ยน
- คิวรันพร้อมงานตั้งเวลาใน `runJobs()` (timer ทุกนาที, `GET <api>/jobs/run`, `easy-cms run-scheduled`)
  ก่อนส่งจะ "จอง" รายการโดยเลื่อน `nextAttemptAt` ออกไป 5 นาที เพื่อไม่ให้หลาย process ส่งซ้ำพร้อมกัน
- ถ้า webhook ถูกลบจาก config รายการที่ค้างของ URL นั้นจะถูกลบทิ้ง

**ค้นหาข้างในบล็อก**
- `layout.blockType`, `layout.<field>`, `layout.<group>.<field>`, `layout.<field>.<locale>` และ `layout: { exists }`
  ชื่อ field หมายถึง field นั้นในบล็อกชนิดใดก็ได้ที่มี และเอกสารตรงเมื่อ "มีบางบล็อก" ตรง (เหมือน array)
- ทำเป็น `EXISTS` บนสมาชิกของ JSON array: SQLite ใช้ `json_each` + `json_extract`, Postgres ใช้
  `jsonb_array_elements` + `#>>` แล้ว cast ตามชนิด field (number/boolean/relationship)
- list ข้างในบล็อก (array, blocks, hasMany) เป็น `EXISTS` ซ้อนกันทีละชั้น แต่ละชั้นมี alias ของตัวเอง (0.8)
- sort ใช้ค่าจากบล็อกแรกที่มี field นั้น (subquery เรียงตามลำดับบล็อก `limit 1`) ส่วน field ใน list ข้างในบล็อก sort ไม่ได้ (0.8)

**SQLite เขียนทีละรายการ (0.8)**
- libSQL เปิด connection ใหม่ทุก transaction และ SQLite มีผู้เขียนได้ทีละคน การเขียนพร้อมกันใน process เดียว
  (เช่น บรรณาธิการสองคน หรือคิว webhook กับการบันทึกเอกสาร) จึงล้มด้วย `SQLITE_BUSY` ตั้ง busy timeout ก็ไม่ช่วย
  เพราะตัวรอของ libSQL บล็อก event loop จนอีกฝั่งทำงานต่อไม่ได้
- dialect ประกาศ `singleWriter` แล้ว adapter จะต่อคิวการเขียนของ process นั้นไว้ Postgres ไม่ได้รับผลกระทบ

**ย้ายข้อมูลเมื่อเปลี่ยน `defaultLocale`**
- snapshot ที่เก็บ (ไฟล์ migration และตาราง migrations) บันทึก `easyCms.localization` ไว้ข้าง snapshot ของ drizzle-kit
  (ตัดออกก่อนส่งให้ drizzle-kit)
- เมื่อภาษาเริ่มต้นเปลี่ยน migration จะเป็นลำดับ เพิ่มคอลัมน์ → `UPDATE` ย้ายค่า → ลบคอลัมน์
  (ใช้ขั้น union ที่มีอยู่แล้ว) การย้ายทำสามคำสั่งต่อตาราง: คัดลอกค่าภาษาเดิมออก, ล้างคอลัมน์หลัก, เติมค่าภาษาใหม่
  การล้างก่อนทำให้ unique index ไม่ชนระหว่างย้าย
- ตารางลูกที่ localized ไม่ต้องย้าย เพราะทุกแถวมี `_locale` อยู่แล้ว (มีแค่ค่า default ของคอลัมน์ที่เปลี่ยน)

## ผลที่ตามมา

- ✅ event ไม่หายเมื่อ restart หรือ serverless หยุด ปลายทางกันซ้ำได้ด้วย `x-easy-cms-delivery`
- ✅ กรองหน้าตามชนิดบล็อกหรือข้อความในบล็อกได้ทั้งสองฐานข้อมูล
- ✅ เปลี่ยนภาษาเริ่มต้นได้โดยข้อมูลไม่หาย
- ❌ โปรเจกต์ที่มี webhooks อยู่แล้วต้องสร้าง migration ใหม่ (ตาราง `webhook-deliveries`)
- ~~❌ ถ้า process ดับระหว่างการส่งครั้งแรก (ยังไม่ทันบันทึก) event นั้นยังหายได้~~ แก้แล้วใน 0.8 เหลือเพียงช่วงระหว่าง commit เอกสารกับการบันทึกคิว ซึ่งไม่มีการรอ network
- ❌ การเขียน SQLite ใน process เดียวกันต้องรอกัน (ปกติเร็วมาก) ส่วนหลาย process ที่เขียนไฟล์เดียวกันยังชนกันได้
- ❌ การค้นในบล็อกต้องอ่าน JSON ทุกแถว ช้ากว่าคอลัมน์ที่มี index
- ❌ snapshot จากก่อน 0.7 ไม่มีข้อมูลภาษา การเปลี่ยน `defaultLocale` ครั้งแรกหลังอัปเกรดควรสร้าง migration ก่อน
